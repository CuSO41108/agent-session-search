# 阶段六：故障注入、迁移与发布

## 目标

用可重复的故障注入证明事务合同，而不是只用正常路径测试“看起来成功”。同时定义旧 Workflow 兼容、灰度和发布门槛。

## 故障注入矩阵

### 事务与文件

- baseline 冻结后崩溃；
- 保存点写入中崩溃；
- 文件提交前、提交中、提交后崩溃；
- 隔离目录丢失或磁盘空间不足；
- 用户在运行期间修改真实工作区；
- 全量回滚遇到文件冲突。

### 外部操作

- planned 写入前崩溃；
- apply 成功、receipt 写入前崩溃；
- inspect 返回 `applied/not_applied/unknown`；
- 补偿中途崩溃；
- 补偿失败；
- API 返回超时但远端已接受；
- 消息发送后无法撤回。

### Agent 与脚本

- required tool 失败但 Agent 输出漂亮 JSON；
- 工具历史被截断或顺序异常；
- Agent 重复调用已成功操作；
- 脚本 exit 0 + stderr；
- 脚本输出类型错误；
- 脚本超时但子进程仍存活；
- 非幂等脚本重试；
- 并行节点一个失败、其他节点仍运行。

每个场景都要验证事务状态、节点状态、账本、报告、快照清理和用户可选动作。

## 旧 Workflow 迁移

- 没有事务合同的旧 Workflow 映射为 `direct`；
- 启动时显示不能保证回滚的警告；
- 只有补齐节点 effectMode、幂等策略和适配器后才能升级为 `controlled` 或 `strict_atomic`；
- 不根据提示词、脚本名称或历史表现推断安全性；
- 旧 Run 只做兼容读取，不伪造缺失 receipt 和快照。

## 预检门槛

严格模式启动前必须检查：

- 隔离环境可用；
- 受治理路径可快照；
- 磁盘空间足够；
- 所有外部写操作存在适配器或被标记为延迟提交；
- 所有脚本具备副作用合同；
- 审批和恢复 UI 可用；
- 账本持久化服务可写。

任何一项不满足都阻止启动，用户可以修改 Workflow 或重新选择模式。

## 灰度顺序

1. `direct` 模式只接入观测和报告；
2. `controlled` 模式接入审批、WAL 和未知状态；
3. 文件 `strict_atomic`；
4. HTTP 可查询/可补偿适配器；
5. 消息草稿与提交点；
6. 完整 Agent/脚本节点验收和保存点；
7. 新 Coding Workflow 默认 `strict_atomic`。

## 发布验收

- 类型检查、事务/恢复/适配器/节点/Renderer 聚焦测试通过；
- 故障注入矩阵有可重复结果；
- `npm run release-note:check` 通过；
- `git diff --check` 通过；
- 文档链接和状态合同与当前实现一致；
- 旧 Workflow 启动警告和新 Workflow 原子预检均可验证。
