# AI Skill 深度探索设计

## 背景

当前 Skill 页面的“AI 探索”只让 Runtime 把自然语言需求改写成 1–3 个英文关键词。随后程序查询 `skills.sh`、按搜索名次和安装量排序。Runtime 看不到搜索结果，也没有阅读候选 Skill 的内容，因此最终列表缺少基于实际内容的描述和匹配判断。

`skills.sh` 搜索接口目前只提供名称、来源和安装量，不提供可直接展示的描述。详情接口会返回 Skill 文件，其中 `SKILL.md` 可作为描述和匹配判断的事实来源。

## 目标

- AI 根据用户需求生成搜索词，并从实际读取过的候选中选出最匹配的前 5 个。
- 每个最终结果展示一句功能描述和一句匹配理由。
- 将额外延迟控制在两次串行模型调用；搜索请求和详情请求全部并行。
- 最多深读 12 个候选，避免读取整个搜索结果集。
- 保持导入行为不变：AI 只推荐，用户仍需手动加入 Skill 库。

## 非目标

- 不创建长期 AI 探索 Session，也不复用上一次探索上下文。
- 不引入 Agent 工具循环或新的 MCP Server。
- 不允许 AI 自动下载到 Agent 安装目录或自动启用 Skill。
- 不抓取 Git 仓库或读取搜索结果集中的全部 Skill。

## 架构

探索分为两个模型阶段，由现有 Runtime one-shot 执行链路完成：

1. **搜索规划**
   - 输入用户原始需求和界面语言。
   - Runtime 返回 1–3 个英文搜索词，以及一条用户语言的需求解释。
2. **候选评审**
   - 程序并行查询全部搜索词。
   - 程序构造最多 12 个具有查询多样性的候选。
   - 程序并行读取候选详情，并为每个候选提取有长度上限的 `SKILL.md` 内容。
   - Runtime 仅能从这些已读取候选中选出最多 5 个，返回排序、描述和匹配理由。

现有 `SkillService` 继续负责 Runtime 调用和 `skills.sh` 客户端编排；纯解析、候选选择和验证逻辑保留在 `skill-ai-search` 领域模块中。UI 和 IPC 继续使用当前的一次请求/响应模型。

## 候选选择

- 每个规划查询最多使用搜索接口第一页。
- 对每个查询按原始名次轮询取候选，使每个查询都能贡献靠前结果。
- 去重后不足 12 个时，再按现有综合分数补齐。
- 综合分数继续以搜索名次为主要信号，安装量只作为很小的次要信号。
- 最多选择 12 个候选；候选少于 12 个时不补造结果。

这种方式避免单个宽泛查询占满候选池，同时仍保留当前搜索排名的有效信号。

## 详情读取与上下文控制

- 候选详情通过现有 `SkillsShClient.getDetail` 并行读取，并复用其 15 分钟缓存与离线旧缓存回退。
- 每个候选只向 Runtime 提供稳定身份、名称、来源、安装量和 `SKILL.md` 文本。
- 单个 `SKILL.md` 最多提供 6,000 个字符，优先保留文件开头的 frontmatter、描述和主要使用说明。
- 详情读取失败不会终止其他请求。
- 至少成功读取一个候选时可以继续评审；不足 5 个可用候选时返回实际数量并标记为部分结果。

## AI 输出与验证

候选评审 Runtime 必须返回一个 JSON 对象：

```json
{
  "recommendations": [
    {
      "id": "owner/repo/skill-id",
      "description": "一句基于 SKILL.md 的功能描述。",
      "reason": "一句说明它为什么匹配当前需求。"
    }
  ]
}
```

程序必须执行以下验证：

- `id` 必须属于本次成功读取详情的候选。
- 去除重复 ID，并保持 AI 返回的顺序。
- 最多接受 5 个推荐。
- 描述和理由必须是非空字符串，并分别限制为 300 个字符。
- AI 返回非法 JSON、虚构 ID，或没有任何有效推荐时，整次探索报错，不使用程序生成的伪描述兜底。

最终结果沿用原始 `SkillsShEntry`，并附加 `description` 和 `reason`。`partial` 在搜索请求失败、详情读取失败、可用候选不足 5 个或有效推荐不足 5 个时为 `true`。

## UI

- AI 探索完成后只展示 AI 选出的最多 5 个结果，不再展示全部关键词搜索结果。
- 每个结果行显示名称、来源、安装量和一句功能描述。
- 选中结果后，详情区在原始 `SKILL.md` 之前显示匹配理由。
- 顶部继续展示需求解释和实际使用的搜索词。
- “加入 Skill 库”行为不变，仍由用户显式点击。
- 探索期间沿用现有加载、重试和请求版本保护，避免旧请求覆盖新请求。

## 性能和失败处理

- 总共固定为两次串行 Runtime 调用。
- 同一阶段的 1–3 个搜索请求并行执行。
- 最多 12 个详情请求并行执行，并依赖现有缓存降低重复探索延迟。
- 不因单个搜索或详情失败而取消其他成功结果。
- 第二次 Runtime 调用失败或输出不可验证时展示错误并允许整次重试。
- 不在 UI 中伪装未读取候选的描述，也不自动降级回只有名称的旧 AI 结果。

## 测试

- 领域测试覆盖查询计划解析、查询多样性候选选择、详情失败、内容截断、推荐解析、虚构和重复 ID、前 5 限制以及 `partial`。
- Service 测试覆盖同一配置 Runtime 被调用两次、搜索和详情输入正确、候选详情缓存映射以及最终结果缓存供预览和导入。
- IPC 和 preload 类型测试覆盖扩展后的结果结构。
- UI 源测试覆盖描述与匹配理由展示，并保持 AI 探索按钮行为。
- 运行类型检查、全量测试、构建和发布说明校验。
